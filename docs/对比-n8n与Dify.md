# 对比：n8n 与 Dify（第一轮，2026-10-16）

同一需求：“给一个网址，抓取网页，用本地模型三句话中文总结”。两边都接同一个本地模型 `shiguang-qwen3-8b:workbench`（Ollama）。

## 结果

| 项目 | n8n 2.43.7 | Dify 1.17.1 |
|---|---|---|
| 运行方式 | npm 直接装在 Windows 上 | Docker，15 个容器 |
| 磁盘 | 2.1 GB 程序 + 51 MB 数据 | 约 11.2 GB 镜像（E:\Docker） |
| 内存（空闲） | 约 0.3 GB | 约 4.7 GB |
| 接本地模型 | 内置 Ollama 节点，填地址即可 | 需先从插件市场装 Ollama 插件，再逐项填模型参数 |
| 首次运行结果 | **空回答**：模型默认开“思考”，且自带 128 token 输出上限，全部被思考吃掉；需手动在节点选项里关思考、调大上限 | 正常：自动把思考过程折叠，只显示回答 |
| 耗时 | 约 4 秒（关思考后） | 约 6 秒（含思考） |
| 用文件导入工作流 | 命令行 `n8n import:workflow`，无需登录 | 只能网页导入；“从 URL 导入”被 SSRF 防护拦下本机地址，最后通过已登录页面调用导入接口完成 |
| 工作流文件可读性 | JSON，节点+连线，类型和版本号要和安装版本对上 | YAML，节点+连线，变量引用写作 `{{#节点.字段#}}` |
| 对外暴露 | 只听 127.0.0.1 | 网页只绑 127.0.0.1（插件调试端口 5003 仍对所有地址开放） |

两边总结内容几乎一致：
> 该网页用于文档示例，无需许可即可使用。此域名不是服务，不建议用于测试和监控。页面采用简洁的样式。

## 对“E:\工作流”设想的启示

1. **“节点 + 连线 + 类型化端口”的图结构，两家和我们的规范本质相同**。这说明方向是主流的，规范不需要推倒重来；以后可以写转换器把我们的图导出成 n8n JSON 或 Dify YAML。
2. **模型细节最容易出错**：n8n 的空回答正是我们规范里“模块要写清行为、例子要能验证”的价值——`llm.think` 一开始就关了思考，所以没踩坑。校验器以后可以加一条“运行示例输入，输出不能为空”。
3. **自然语言生成图这一步两家都没在本轮验证**。n8n 的 AI 生成工作流功能通常要接云端；Dify 主要提供提示词和代码的 AI 生成。“完全本地、带校验反馈的自然语言 → 图”仍是我们方案的差异点，下一轮应该专门测这一项。
4. **重量**：Dify 功能全但重（4.7 GB 内存常驻）；n8n 轻得多。我们自己的引擎如果只做“模块 + 图 + 执行 + 校验”，可以比两者都轻。

## 下一轮建议

- 同一需求换成批量版本（循环 + 条件，对应 `examples/summarize_many.workflow.json`），比较两家表达条件分支和循环的方式。
- 专门测试“用一句话描述需求 → 生成工作流”：两家能否在不接云端的情况下做到，生成结果需要改几处。
