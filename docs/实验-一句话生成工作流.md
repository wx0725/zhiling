# 实验：一句话生成工作流（2026-10-16）

目标：只用本地模型（`shiguang-qwen3-8b:workbench`，Qwen3-8B），从一句中文需求生成符合接口规范的工作流图。
代码：`tools/generate.py`；测试题：`evals/generation_cases.json`；运行：`python -m evals.run_generation`；原始结果：`evals/results/`。

## 测试题

| 题 | 难度 | 需求要点 |
|---|---|---|
| L1 | 1 | 抓一个网页原样输出 |
| L2 | 2 | 抓网页 + 一句话总结 |
| L3 | 3 | 状态码 200 就总结，否则说明打不开（条件分支） |
| L4 | 4 | 一组网址逐个总结（循环） |
| L5 | 5 | 循环 + 条件 + 合并 |
| X1 | – | 翻译后发邮件（没有发邮件模块，应如实拒绝） |

## 结果演进

| 版本 | 改动 | 校验通过 | 说明 |
|---|---|---|---|
| v1 | 用正式 schema 约束输出 | 0/6 | Ollama 不支持 schema 里的 allOf/if-then，反而**禁止模型写 module 字段**，三轮输出完全相同 |
| v2 | 改为普通 JSON 模式 | 2/6 | 简单题能过；条件、循环全错；不会拒绝 |
| v3 | 扁平版约束格式（`schemas/workflow.gen.schema.json`） | 2/6 | 同上：问题不在格式，而在模型没见过条件/循环 |
| v4 | ① 加两个**换了场景**的教学例子（客服回复的 if/merge、逐句翻译的 foreach）② 修正时给“错误 + 具体改法”，重新组织对话、重试加随机性 ③ 生成前先判断可行性 | 5/6 | 循环、复杂题通过；X1 如实拒绝 |
| v5 | 配置冲突的提示点名具体端口 | **6/6** | 平均每题 1–3 轮，2–17 秒 |

## 人工复查：校验通过 ≠ 做对

逐张检查 v5 的数据流向：

- L1、L2、L4 正确；X1 正确拒绝（“发送邮件的功能没有对应的模块实现”）。
- **L3、L5 有同一个语义错误**：传给“总结”节点的是网址（`$in.url → branch.value`），而不是网页内容 `fetch.text`。结构完全合法，校验器发现不了，运行后会去“总结一串网址”。
- 原因很可能是教学例子“客服回复”里，往下传的恰好就是原始输入；模型照搬了这个模式。

**诚实成绩：结构校验 6/6，语义正确 4/6。** 没有再针对这两题改提示词，以免变成对着考题教答案。

## 结论

1. **本地 8B 模型能完成这件事**，前提是三样东西都在：模块说明带例子、覆盖各类结构的教学例子、能指出“错在哪 + 怎么改”的校验反馈。三者缺一，成绩就掉到 0–2/6。
2. **校验器是关键**：它让一个小模型通过 1–3 轮自我修正达到结构全对；同样的错误信息如果不附改法，模型会原样重复。
3. **只有结构校验不够**，必须实际运行：下一步的执行引擎应提供“用示例输入跑一遍、检查各节点输出是否合理”的能力，把 L3/L5 这类语义错误拦下来。这也会成为以后训练专用小模型的数据来源。
4. 题量很小（6 题），并且 L5 与教学例子结构相近，结论只能说明可行性，不能说明稳定性；后续要扩充题库并加入与例子差异更大的题（已扩充，见下文“扩充题库”）。

## 换用 27B（qwen3.8:27b-q4_K_M）

27B 的模型文件放在另一块盘上，默认的 Ollama 看不到它；另开一个 Ollama（端口 11435，`OLLAMA_MODELS` 指向那个目录，只用一块显卡）运行，原服务不动。生成器通过环境变量 `WORKFLOW_OLLAMA_URL` 选择服务。

过程中修了两处问题，修完后两个模型都在**相同代码、相同 JSON 模式**下重跑：
- 扁平约束格式让 27B 不写 `config`（约束固定了字段顺序，模型倾向提前结束对象）；不加约束时第一轮就写对。扁平约束对 8B 也没有带来提升，**默认改为普通 JSON 模式**。
- 可行性判断原先把“没有对应模块的步骤”一律当作缺能力，误拒了 L5（“输出列表”本由循环结构完成）；改为以模型给出的 feasible 结论为准。

| | 8B（shiguang-qwen3-8b） | 27B（qwen3.8 q4_K_M） |
|---|---|---|
| 结构校验 | 6/6 | 6/6 |
| **语义正确（人工复查）** | **4/6**（L3、L5 把网址当成网页内容传给总结） | **6/6** |
| 修正轮数 | L3 用 2 轮、L5 用 3 轮 | 全部第 1 轮通过 |
| 单题耗时 | 1–25 秒 | 4–33 秒 |
| 显存 | 约 5 GB | 约 17.7 GB（24 GB 显卡） |

27B 还会做更合理的取舍：需求里给定了网址时，直接写进固定参数而不是多设一个输入。小瑕疵：L5“说明原因”的指令写“根据状态码”，实际传入的是错误页面内容。

**结论更新**：生成这一步用 27B 明显更可靠（不需要修正、语义无误）；8B 更快，适合作为执行时的“思考”模块。以后若训练专用小模型，可用 27B 生成并经运行验证的图作为训练数据。

## 扩充题库：与教学例子差异更大的 9 道新题

受限于目前只有 3 个模块，“差异更大”体现在结构和数据类型上，而不是新能力：

| 题 | 考点 |
|---|---|
| N1 | 只用比较、不用模型，输出布尔值 |
| N2 | 两个输入、两次抓取，比较两边都来自连线 |
| N3 | 两个思考模块串联（先总结再翻译） |
| N4 | 数字输入、大小比较，分支里没有文本可传 |
| N5 | 先用模型判断语言，再把文字结果转成条件；另一支原样输出 |
| N6 | 循环里只有比较，输出布尔列表 |
| X2 | 需要定时 + 写文件（应拒绝） |
| X3 | 需要读本地文件（应拒绝） |
| X4 | 能拼出循环，但没有“列表合成一段文字”的模块，类型接不上（应拒绝） |

修了一个自己的 bug 后两模型各跑一遍（结果：`evals/results/20261016-222007-*27b*`、`20261016-222208-*8b*`）。bug：规则让拒绝时“保留输入输出、节点为空”，但校验器要求每个输出都有来源，导致 27B 在 X4 里已经写出“无法实现：缺少把列表转成文字的模块”仍被判失败；现在生成阶段给出“无法实现”即按拒绝处理。

| | 8B | 27B |
|---|---|---|
| 自动判分（全 15 题） | 12/15 | 14/15 |
| 其中原题 / 新题 | 6/6 / 6/9 | 6/6 / 8/9 |
| **人工复查语义正确** | **9/15** | **14/15** |
| 语义错误 | L3、L5 把网址当网页内容；N5 用“原文是否包含‘非英文’四个字”判断语言 | 无 |
| 未通过 | N1（把布尔值接到需要文本的模型上，再把文本接到布尔输出）、N4、X4（没拒绝，硬把列表接到文本） | N4 |
| 修正轮数 | 部分题 2 轮 | 除 X4 外全部首轮 |

27B 的亮点：N5 让模型只输出 `EN`/`OTHER` 再用比较转成条件，另一支直接把原文送进 merge，没有多调一次模型。8B 在重试时有随机性，同一题两次运行结果可能不同（N1 第一次通过、第二次失败）；每个模型只跑了一遍，结论只说明大致水平。

**规范缺口（N4，两模型都卡住）**：`if` 必须有一个要往下传的 `value`，但“按分数写一句话”这类需求只需要决定走哪条路，分支里没有数据可传；硬接分数（整数）又接不到需要文本的模型。规范 v0.2 需要二选一：允许 `if` 不带 `value` 只做路由，或增加“把值转成文字”的模块（例如 `text.format`）。X4 同理说明需要“把列表合成文字”的模块（例如 `text.join`）。

## 生成后实跑检查（规范 v0.2 + 执行引擎）

结构校验通过后，再做一步**运行检查**（`tools/semantic.py`）：
1. 审查模型按测试题的提示编 2 组示例输入，有分支时两组分别走两侧（如能打开/打不开的网址、及格/不及格的分数）；
2. 执行引擎用真实模块实际运行（思考模块用 8B），记录每个节点收到的输入和产生的输出；
3. 审查模型（27B）阅读运行记录，找出“节点收到的数据不对、条件没检查对、输出不满足需求”的问题，并给出符合规范的改法；
4. 有问题就连同改法反馈给生成模型重写，算作一轮。运行出错（如节点报错）直接反馈，不经审查模型。

两处调整：
- 审查模型起初不知道模块清单和连线规则，诊断准确但改法常不合规范（如“再加一条线”导致一个输入两条线、建议不存在的 regex 比较）；把模块清单和关键规则交给它之后，改法变得可执行。
- 生成器与思考模块原先共用一个环境变量选择 Ollama 服务，运行检查时思考模块被带到 27B 的服务上而报“模型未安装”，27B 因此误判为无法实现；改为生成器用独立的 `WORKFLOW_GEN_URL`。修正后重跑，此前的结果作废。

| 配置（15 题） | 交付的图 | 其中语义正确 | **交付了错误的图** | 单题耗时 |
|---|---|---|---|---|
| 8B 生成，无运行检查（规范 v0.1） | 12 | 9 | **3**（L3、L5、N5） | 1–25 秒 |
| 8B 生成 + 27B 运行检查（v0.2） | 10 | 10 | **0** | 8–110 秒 |
| 27B 生成，无运行检查（v0.1） | 14 | 14 | 0 | 4–33 秒 |
| 27B 生成 + 27B 运行检查（v0.2） | **15** | **15** | 0 | 3–85 秒 |

（结果文件：`20261016-222208-*8b*`、`20261016-231306-*8b*-check-*`、`20261016-222007-*27b*`、`20261016-230518-*27b*-check-*`。语义正确均为人工逐张复查。v0.1→v0.2 期间 N4 由“规范表达不了”变为可实现，X4 改为可实现的 N7。）

观察：
- **运行检查的价值在于“错的图不交付”**：8B 的 3 个语义错误全部被发现，8 张本来正确的图没有一张被误报。
- **发现之后能不能改对，取决于生成模型**：8B 拿到准确的改法后有时能改对（单独重跑时 L5、N5 改对了），有时改不对（L3 多次失败）；27B 第一轮只有 L3 有问题，收到反馈后第二轮就改对了，并且改得很好——用 `text.format` 生成“网页打不开（状态码：404）”，再用控制线决定何时使用。
- 27B 会主动使用 v0.2 的控制线和新模块：L5、N4 用控制线路由；N7 完整走通“逐个总结 → text.join → 整体总结”。
- 代价是时间：每张图要多跑一次示例并多一次 27B 审查，单题从十几秒增加到几十秒。
- 仍然只有 15 题、每种配置一次运行，审查模型也可能漏判（8B 的 N7 只拼接不总结，第一次审查放过了，补充规则后才被指出）。

**当前推荐配置**：27B 生成 + 运行检查。8B 可留作快速草稿或离线时的后备。

### 回归重跑（2026-10-17，三轮代码审查修复之后）

同一配置（27B 生成 + 27B 运行检查）重跑全部 15 题，确认审查修复（取消检查、回答形状校验、示例输入规则、引用快照、执行顺序算法、类型推断缓存等）没有让生成效果退步。结果：`evals/results/20261017-012754-*27b*-check-*`。

| | 交付的图 | 其中语义正确 | 交付了错误的图 | 单题耗时 |
|---|---|---|---|---|
| 2026-10-16 | 15 | 15 | 0 | 3–85 秒 |
| 2026-10-17 重跑 | **15** | **15** | 0 | 3–78 秒 |

- 12 题第一轮就通过结构校验和运行检查，3 道不可实现的题如实拒绝。
- L5 第一轮把 if 的 then/else 接到了数据输入（if 没有接 value），被结构校验拦下并给出改法，第二轮改成控制线后通过；这次的失败原因页说明改为“根据状态码说明可能原因”，比上次（指令写状态码、实际传入网页内容）更贴合。
- 上次 L3 第一轮被运行检查指出问题，这次第一轮就正确。每题只跑一次，模型有随机性，这类差异不说明能力变化。
- 语义正确为人工逐张复查。小瑕疵：N4 的祝贺/鼓励语没有带上分数本身（需求没有要求）。

## 扩充模块库：13 个模块、27 道题（2026-10-17）

新增 8 个模块：提取正文 `html.text`、拆分文字 `text.split`、查找匹配 `text.find`、取字段 `data.get`、列表统计 `list.stats`、筛选列表 `list.filter`、读取文件 `file.read`、写入文件 `file.write`。新增 12 道题（M1–M10 可实现，X5、X6 应拒绝）：

| 题 | 考点 |
|---|---|
| M1 | 抓取后先提取正文再总结 |
| M2 | 文字按行拆成列表，逐行翻译 |
| M3 | 不用模型，用规则从网页里找邮箱 |
| M4 | 从 JSON 文字里取字段再比较，输出真假 |
| M5 | 先求平均再分支，分支里没有文本可传 |
| M6 | 循环里判断能否打开，循环外筛选（循环本身去不掉项） |
| M7 | 循环判断 + 筛选 + 求和，全程不用模型 |
| M8 | 读本地 txt 再总结 |
| M9 | 读 csv、按行拆、数个数 |
| M10 | 总结后写文件（运行检查只演练） |
| X5 | 读 Word（读取模块只支持文本类文件） |
| X6 | 发到微信（没有发消息的模块） |

为让题目可重复：M 题用到的网页由跑题库时启动的本地服务提供（`evals/fixtures/site`，端口 8799），文件题用 `evals/fixtures` 里的示例文件。写文件在运行检查里不真的写：模块提供 `runtime.dry_run` 演练入口，检查时引擎改调演练（同样在独立进程里，可停止）；网页上运行前会弹窗确认。

同一配置（27B 生成 + 27B 运行检查）跑了三次，每次之间按发现的问题改模块：

| 次 | 结果 | 发现的问题 → 改法 |
|---|---|---|
| 1 | 26/27 | M9：“列表统计”只输出小数类型，数出的行数接不到整数输出，三轮都卡在类型上 → 增加整数输出 `count` |
| 2 | 26/27 | N1（原题）：模型用“提取正文”后查 Example，但 example.com 正文里只有小写 examples，大写的在标题里，而标题不在 text 里；运行检查正确指出，模型却没有办法把标题和正文合到一起 → 提取正文默认把标题放在 text 第一行（可关） |
| 3 | **27/27** | 无。结果：`evals/results/20261017-164333-*27b*-check-*` |

第 3 次的人工复查：27 张图逐张看连线和样例输出，语义全部正确，3+2 道应拒绝的题理由准确（X3、X5 引用了读取模块“不支持 PDF/Word”的说明，X6 引用了写入模块“不能发送到别处”）。除 L5 外全部第一轮通过。

- 新模块被主动用上：L2、L4、N3、N7、M10 自己加了“提取正文”；M1、M3 需要纯正文时会把 `include_title` 关掉。
- M6、M7 走通了“循环里判断 → 循环外筛选”这个新模式；M9 用的是新加的整数 `count`。
- 小瑕疵：L5 的“说明原因”指令里留了字面的 `{value}`（思考模块不替换占位符），但传进去的文字就是状态码，回答正确。M1 遇到打不开的网页时总结的是错误页（需求没要求区分）。
- 仍然每题只跑一次；第 1、2 次的失败都暴露的是**模块设计**问题（输出类型、标题去哪），不是生成能力问题，修模块比改提示词更治本。

## 与 n8n / Dify 的对照（本轮状态）

- **n8n**：AI 搭建入口（n8n Assistant）可以通过环境变量 `N8N_INSTANCE_AI_MODEL=openai/<模型>`、`N8N_INSTANCE_AI_MODEL_URL=http://127.0.0.1:11434/v1` 指向本地 Ollama，界面已识别到模型；但**必须先配置代码沙箱**（免费方案需要 Docker，另一方案为付费云服务）才能使用。本地模型经 OpenAI 兼容接口的工具调用已单独验证可用（单次约 30 秒，含思考）。
- **Dify**：有工作流生成器（Ctrl+K → `/create`，先规划节点再逐个生成，最后自动排版和校验），使用请求里指定的模型，理论上可用本地 Ollama。
- 两者的实测都在等 Docker 修复（WSL 无权挂载 E:\Docker\data 下的磁盘），尚未完成。
